# 电视真机播放性能与兼容性排查

> 排查日期：2026-09-05  
> 目标设备：小米电视 192.168.31.221:5555（MiTV-MFTP0 / alita）  
> 对照设备：本机模拟器 emulator-5554  
> 测试频道：CCTV-13 官网直播页  
> 排查范围：只做运行时诊断和兼容性实验，不修改频道来源，不采集、存储或转发直播流。

## 1. 问题现象

- 本机模拟器频道加载较快，播放过程基本流畅。
- 小米电视加载频道明显更慢，播放过程中频繁卡住，有时会重新显示“正在加载直播…”。
- 电视使用有线网络，基础连通性和延迟正常。

## 2. 结论

问题的主因是电视上的旧版 Android System WebView 与 CCTV 当前网页播放器、MSE 媒体管线及厂商硬件解码器之间存在兼容性问题。

电视性能较弱、系统后台进程占用较高，会放大加载慢和卡顿，但不是根因。网络问题、内存不足和纯 CPU 软件解码均已基本排除。

关键链路如下：

    CCTV 当前网页播放器
      → WebView 66 的 WebRTC / MSE 实现无法完全兼容当前播放器
      → 视频分片出现负 DTS，MSE appendBuffer 失败
      → 厂商 H.264 解码器反复 flush / 重建
      → 视频几秒一卡、重新缓冲，最终可能一直停在加载页

当前 App 在 MainActivity.kt 中固定使用 Chrome 124 桌面 UA，但电视实际 WebView 内核只有 Chromium 66。这个差异会增加站点向旧内核下发现代播放器逻辑的风险；不过真机 A/B 结果证明，单独调整 UA 无法解决问题。

## 3. 设备对照

| 项目 | 模拟器 | 小米电视 |
|---|---|---|
| Android | 12 / API 32 | 9 / API 28 |
| ABI | arm64-v8a | armeabi-v7a，32 位系统 |
| CPU | 虚拟高性能 CPU | 4 核 Cortex-A73，最高 1.3 GHz |
| 内存 | 约 6 GB | 约 2.7 GB |
| GPU | Adreno 640 | Mali-G52 |
| WebView | 95.0.4638.74 | 66.0.3359.158 |
| WebView 多进程 | 开启 | 关闭 |
| 直播视频 | 正常播放 | 频繁重建播放器 |

电视系统中只有一个有效 WebView provider：

    com.android.webview 66.0.3359.158

没有已安装、可直接切换的新版 Chrome/WebView provider。普通侧载不同签名的 WebView APK 通常也无法替换系统 provider，需通过电视固件或厂商认可的更新渠道处理。

## 4. 已排除项

### 4.1 网络不是主要瓶颈

电视实际走有线接口 eth0，不是 Wi-Fi。到 tv.cctv.com 的测试结果：

    10 packets transmitted, 10 received, 0% packet loss
    rtt min/avg/max = 6.558/9.856/32.742 ms

模拟器平均延迟约 10.6 ms，与电视接近。电视在测试窗口内也持续收到直播数据，因此不是“网络完全断流”。

这只能排除基础网络质量问题；CDN 分配和长时间链路抖动仍可能影响体验，但无法解释电视端稳定复现的媒体解析错误。

### 4.2 不是纯 CPU 软件解码

电视已经调用厂商硬件 H.264 解码器：

    OMX.MS.AVC.Decoder
    video/avc
    1280x720

因此不是因为电视用 CPU 软解 1080p 而必然卡顿。真正的问题发生在 MSE 分片解析、解码器输出缓冲配置和播放器重试流程。

### 4.3 不是内存不足或 OOM

排查时电视内存状态正常，约有 900 MB 可用/可回收内存，没有出现 OOM 或 LMK 杀进程记录。

不过播放器反复失败重建会显著增加资源消耗：

- App 常规测试时 PSS 约 356 MB。
- 频繁重试时 RES 可增长到约 429–515 MB。
- 这是播放失败的放大结果，而不是最初触发原因。

## 5. 关键日志证据

电视在同一个 CCTV-13 页面上，大约每 3–5 秒重复出现以下日志：

    MediaEvent: MEDIA_ERROR_LOG_ENTRY
    video frame with PTS ... has negative DTS ...
    Append: stream parsing failed

    [OMX.MS.AVC.Decoder]
    setPortMode on output to DynamicANWBuffer failed w/ err -1010
    MS_OMX_FlushPort

    Failed to parse SessionDescription
    a=extmap-allow-mixed Expects at least 2 fields

一次基线采样累计出现：

| 错误 | 电视 | 模拟器 |
|---|---:|---:|
| MSE Append: stream parsing failed | 43 | 0 |
| WebRTC SDP 解析失败 | 22 | 0 |
| 解码器输出模式失败 | 43 | 0 |
| 解码器 flush | 41 | 0 |

错误模式说明：

1. WebView 66 无法接受播放器追加的部分媒体分片，日志显示 DTS 在应用时间偏移后为负数。
2. CCTV 的 P2P/WebRTC 路径包含旧内核无法解析的 SDP 字段。
3. 每次媒体解析失败后，播放器重新创建 OMX.MS.AVC.Decoder。
4. 反复初始化、销毁解码器导致 CPU、内存和渲染负担增加，并产生肉眼可见卡顿。

## 6. 性能侧的次要问题

电视自身还有一个独立的系统负载问题：com.xiaomi.wakeupservice。

采样时该服务长期占用约 58%–72% 的一个 CPU 核心。电视只有 4 个最高 1.3 GHz 的核心，这会明显压缩 WebView、SurfaceFlinger 和媒体线程的调度余量。

其他观测：

- 电视播放失败重试时 App CPU 一度达到约 140%–170%。
- 电视 UI 统计约 4.22% janky frames，模拟器对应测试为 0%。
- 电视 load average 约 64，但厂商电视内核存在大量长期 D 状态媒体/电视服务线程，所以该数值不能直接按普通 Linux 主机方式解释为 CPU 满载。

后台语音服务值得单独处理，但即使停止它，也不能修复已经明确出现的 MSE、SDP 和硬件解码接口兼容错误。

## 7. 已验证的兼容方案

所有实验都在电视真机安装 APK、清空日志、重启 App 后测试，并检查实际画面和媒体日志。实验结束后已撤回补丁并重新安装原始稳定版本。

### 7.1 桌面 UA 从 Chrome 124 改为真实 Chrome 66

结果：无改善。

CCTV 仍然下发相同播放器，媒体分片解析失败和解码器重建继续发生。只修改 UA 中的版本号不足以让网站选择旧播放器。

### 7.2 使用 WebView 默认 Android UA

结果：无改善。

官网会跳到移动版 /m/ 页面，但移动页仍加载相同的 liveplayer.js，继续使用 WASM/MSE/P2P 相关播放逻辑。

测试窗口内仍出现：

- 15 次媒体片段解析失败；
- 15 次解码器输出模式失败；
- 16 次解码器 flush；
- 最终停在“正在加载直播…”。

### 7.3 禁用 CCTV P2P/WebRTC，保留 WASM/MSE

通过 CCTV 播放器已有的 p2p=false 参数关闭 P2P。

结果：只解决了 WebRTC 错误，没有解决播放问题。

- Failed to parse SessionDescription 降为 0；
- HLSP2P 不再加载；
- 但 60 秒内仍有 12 次 MSE 分片解析失败、12 次解码器输出模式失败和 13 次 flush；
- 页面仍无法稳定出画面。

### 7.4 禁用 WASM/P2P，尝试普通 HLS 回退

结果：错误归零，但无法起播。

WebView 66 在该电视环境下不能直接使用 HTML video 原生播放 HLS。播放器没有创建有效视频链路，页面始终停在加载状态。

### 7.5 模拟 iPad Safari，尝试 CCTV 的原生 HLS 分支

结果：错误归零，但无法起播。

CCTV 脚本确实进入了面向 iPad 的原生 HLS 分支，但 Android WebView 66 不具备对应的 Safari 原生 HLS 能力，因此没有建立可播放的视频元素。

### 7.6 禁用 P2P 并为 MSE 增加时间戳偏移

针对日志中约 -5 至 -21 ms 的负 DTS，曾在老 WebView 上尝试给 SourceBuffer.timestampOffset 增加小幅正向偏移。

结果：失败且会加重重试，不能使用。

- 60 秒出现 71 次媒体分片解析失败；
- 61 次解码器输出模式失败；
- 48 次解码器 flush；
- App CPU 约 172%，内存约 515 MB。

这说明问题不是固定时间偏移可以修复，而是旧 MSE 与当前直播分片时间轴、append window 或播放器封装方式的整体兼容问题。

## 8. 当前处理状态

- 无效的实验性 UA、P2P/WASM 和 MSE 补丁均已撤回。
- 腾讯 X5 SDK 44286 曾完成代码接入和真机安装，但服务端返回下载状态 -124；从 SDK 字节码可确认该状态表示第三方 App 获得的内核下载地址为空。目标电视最终仍为 isX5Core=false、installedCore=0，因此 X5 方案未保留。
- 当前已改为随 APK 打包的 GeckoView 153，不再依赖电视系统 WebView 或运行时内核下发。
- 现有全屏注入已迁移为内置 WebExtension，并通过 GeckoView native messaging 回传播放状态。
- testDebugUnitTest 和 assembleDebug 均通过。

### 8.1 GeckoView 真机结果

目标电视使用 armeabi-v7a 专用 APK，已确认 Gecko 原生库从 APK 内加载，CCTV 页面可正常播放并铺满 1920x1080 屏幕。

验证结果：

- CCTV-9 连续播放 3 分钟，按 30 秒间隔获取的 6 张截图哈希均不同，画面持续推进；
- 3 分钟内 MSE 分片解析失败、WebRTC SDP 解析失败、周期性解码器 flush 和 Gecko 内容进程崩溃均为 0；
- 菜单打开时视频继续播放；
- 关闭菜单后从 CCTV-9 切换到 CCTV-10 成功；
- 换台后成功播放 CCTV-11；
- 个别频道首次建立硬件解码器时可能出现一次 DynamicANWBuffer 能力协商警告，但未进入周期性重建，播放可继续；
- 主进程 PSS 稳定播放时约 121–148 MB；关闭站点隔离和独立扩展进程后仍有 GPU、内容、媒体等必要子进程，实测合计 PSS 约 577 MB，需要后续继续做长时间内存观测。

构建产物使用 ABI 拆分：

- armeabi-v7a 电视包约 167 MB；
- arm64-v8a 包约 204 MB；
- 不再生成同时包含所有架构的 334 MB 通用包。

最终实现使用 GeckoView 153 而不是 155，因为 GeckoView 155 依赖 Kotlin 2.4 标准库，而当前 AGP 9.3.2 内置 Kotlin 编译器只能读取到 Kotlin 2.3 元数据；GeckoView 153 使用 Kotlin 2.3.21，与当前工具链兼容。

## 9. 后续建议

### 9.1 当前落地：GeckoView

当前版本使用 GeckoView 153 替换系统 WebView 66，已解决目标电视上的周期性媒体解析失败和卡顿问题。下一阶段应重点补齐：

- 更长时间的内存与温度压力测试；
- Gecko 子进程回收和内容进程崩溃恢复；
- 多频道连续切换稳定性；
- 发布包体积评估和签名安装验证。

当前为了降低老电视内存压力，GeckoRuntime 已关闭站点隔离和独立扩展进程。最终配置真机短测仍可全屏播放并正常换台，主进程 PSS 约 148 MB；包含 GPU、内容、工具和媒体进程的合计 PSS 约 570 MB。进程间存在共享内存，该合计值不能直接等同于物理内存增量，但仍明显高于原系统 WebView 方案。

### 9.2 仍可尝试更新系统 WebView 或电视固件

若厂商后续提供新版 WebView，系统内核的包体积和运行内存通常更低，仍值得重新评估。验收标准：

- 能在合理时间内自动出画面；
- 连续播放至少 10–30 分钟；
- Append: stream parsing failed 不再周期性出现；
- 解码器不再每几秒 flush/recreate；
- App CPU 和内存保持稳定。

### 9.3 X5 结论

本次目标电视无法获得 X5 内核下载地址，SDK 自动回退系统 WebView 66，不能解决问题。除非未来改为静态内核交付或腾讯恢复对该设备的内核下发，否则不应将 X5 作为这台电视的默认方案。

### 9.4 评估原生播放器兜底

如果嵌入式浏览器内核仍不可行，可评估 Media3/ExoPlayer 作为老设备专用播放兜底。但必须先确认官方页面是否提供合规、稳定、允许直接播放的公开地址，并继续遵守“不采集、不存储、不转发、不绕过限制”的产品红线。

### 9.5 单独处理电视后台负载

可以在用户确认后，临时停止 com.xiaomi.wakeupservice 做一次 A/B 测试，判断释放约半个至一个 CPU 核心后对启动速度和偶发掉帧的改善程度。

该操作可能影响电视语音唤醒，且不能解决 WebView 66 的媒体兼容问题，因此只能作为性能优化项，不能作为主修复方案。

## 11. 2026-09-06 首次播放性能优化

针对 GeckoView 版本在低性能电视上首次进入播放较慢的问题，已落地以下优化：

- `GeckoRuntime` 移到进程级 `Application`，并调用 GeckoView 150+ 官方提供的 `warmUp()` 预分配首次页面所需子进程；
- 频道模型增加央视频公开页面 `pid`，冷启动直接加载 `https://www.yangshipin.cn/tv/home?pid=...`，不再先进入默认频道再点击目标频道；
- WebExtension 在频道列表出现后核对 `pid` 实际选中的频道，若官网调整 `pid` 则自动回退到按频道名点击；
- 取消 WebExtension 主动点击“蓝光 1080P”，清晰度完全交给央视频官网默认/自适应策略；官网当前仍可能自行默认选择蓝光；
- 只有收到目标请求对应的 `playing` 后才持久化频道，避免失败频道污染下一次冷启动；
- 加入有界恢复链路：页内换台 18 秒超时后直达重载；冷启动 35 秒超时后同频道重试一次；仍失败则回到最近成功频道或 CCTV-9/CCTV-10；
- 侧边菜单 RecyclerView 延迟到首次按确定键时初始化，减少启动主线程工作；
- 增加 `StartupTiming` 分段日志，覆盖 Runtime 预热、Activity、页面、扩展和首帧。
- WebExtension 从每 500ms 全量扫描 DOM 改为事件驱动：`MutationObserver` 发现频道列表和播放器节点，`playing` / `loadedmetadata` / `canplay` / `emptied` 等媒体事件跟踪状态；全屏 DOM 仅在播放器或祖先结构变化时重建，官网改写受控节点样式时再定向修复。

电视实测结果：

- `GeckoRuntime.create + warmUp` 约 198–217 ms；
- Activity 内冷启动到播放成功的正常样本约 24.5–33.4 秒；
- 最终候选版一次正常冷启动约 30.6 秒；
- CCTV-11 首次建链超过 35 秒时触发同频道重载，第二次约 19.8 秒成功出画面，未再无限等待；
- 已有页面从 CCTV-10 切 CCTV-11 约 4.9 秒，从 CCTV-11 切 CCTV-12 约 11.8 秒；
- 未发现 App 崩溃或 Gecko 内容进程崩溃。
- 事件驱动版本冷启动约 33.1 秒；CCTV-1→CCTV-2 约 9.9 秒、CCTV-2→CCTV-3 约 4.2 秒；静置 20 秒截图持续变化且保持 1920×1080 全屏。

结论：低端电视的主要耗时仍位于央视频页面解析和媒体建链，原生 Activity 不是主要瓶颈。当前优化的核心收益是减少无效播放器重建，并把偶发的无限加载转为有边界的自动恢复。
